# 群聊：群里只沟通，干活转后台

## 问题（2026-11-03 苏折竹群实际记录）
- **发言位被占着**：群调度一次只跑一个回合（`rooms/scheduler.ts` 的 `s.current`）。导演 @ 剪辑「拼首段预览」后，剪辑在这个回合里一边装软件一边剪片，持续 40 分钟以上，整个群都在等它。
- **没 @ 人的消息送错人**：有人在跑时，没 @ 人的消息会当插话塞给正在跑的那位（`forCurrent` 默认取 true）。剧本问题送到了剪辑那里，导演要等剪辑整轮做完才能接到。
- **过程刷屏**：成员每想一步就在群里多一条消息，内容是空的，只有「思考 / 1 个步骤 · 全部成功」。
- **上下文只增不减**：只有在「项目交付并且群里没有进行中的项目」时才会整理（0022）。这个群一直有项目在跑，剪辑的群会话涨到 47 万 token，每想一步要约 5 分钟，插话也要等 5 分钟才送得进去。

## 设计
1. **动手就转后台**（与「命令跑 5 秒自动转后台」同一个思路）：成员的群回合满足下列任一条件，就让出发言位：
   - 做完 `DETACH_TOOL_STEPS`（3）个工具步骤；
   - 跑了 `DETACH_MS`（60 秒）；
   - 用户发来一条要交给管理者的消息（见第 3 条）。

   让出后，这个回合在成员自己的会话里继续跑完，不中断、不换会话。群调度不再等它，接着安排下一位。回合结束后，再照原逻辑收尾：
   - 记状态、报错；
   - 派活批次清点、管理者 followup；
   - 调用 `hooks.after`。

   管理者的回合也按同一规则让位。
2. **同一个成员不同时跑两轮**：排到的回合，如果那位成员正在后台跑，就把这一轮的内容当插话送进去（`runtime.send` 的 steer），回合记为完成，不另开一轮。停止群聊时，后台在跑的成员回合一起中止；服务重启时，沿用原来的「中断 + 继续」。
3. **没 @ 人的消息交给管理者**：
   - 正在发言的是管理者：照旧插话给它。
   - 正在发言的不是管理者：先让当前成员回合转后台，再马上排一轮管理者。管理者自己决定是直接回答、改计划，还是转给负责的成员。
   - 管理者本身在后台跑：插话给管理者。
   - @ 了谁就给谁，引用回复照旧只给作者。
4. **群里只显示说的话**：
   - 群消息里只有思考和工具步骤、没有文字的那些，不单独显示。
   - 它们的步骤并进这位成员下一条有文字的消息，显示为那条消息里折叠的「N 个步骤」，过程仍然可以点开看。
   - 成员还在后台干、还没说话时，成员状态显示「在后台干活」。
5. **按大小整理**：成员的一轮群回合结束、它的群会话空闲时，如果上一次调用读入的 token 超过 `TIDY_MIN_TOKENS`（15 万），就只整理这一个成员的群会话，复用 `tidyRoom` 的 Pi 整理和整理说明。
   - 进行中的项目也会整理，整理说明要求保留进行中的任务、答应了没做的事、文件位置和关键决定。
   - 整理期间，这位成员的下一轮先等整理做完。
   - 交付后整理全群的逻辑不变。

## 不做什么
- 不靠管理者判断「这是不是干活」再决定建任务，转后台是机械规则。
- 不把正在跑的回合挪到新会话里，避免助理忘掉上下文。
- 不截断工具输出，不删原始记录。
- 单聊不变。
