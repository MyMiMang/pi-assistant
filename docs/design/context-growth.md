# 群成员单次调用读入过多：数据与方案

## 1. 现象

模型没有记忆，助理每调用一次模型（每调一个工具也算一次），都要把「系统规则 + 工具说明 + 这个助理在这个会话里的全部历史」重新读一遍。每个助理在每个群里只有一个长期会话，群里的事都往后追加，项目结束了也不收拾，所以读入只增不减。

- 开发实测环境的测试管理者（测试群，四个小项目，89 次调用）：第一次读入 1.6 万 token，最后一次 13.8 万。
- 用户真实 App（2026-10-20 只读统计）：「导演」一天 213 次调用，平均每次读入 23.5 万。

影响：回复越来越慢；花费靠缓存命中压着，缓存一失效就整段按全价；早已结束的项目细节可能分散模型注意力。

## 2. 拆开看读进去的是什么

只读统计会话文件，按内容类型分（字符数占比）：

| 内容 | 测试管理者（20.4 万字） | 导演（54.3 万字） |
|---|---|---|
| 每次唤醒附带的项目方案 + 进度清单 | 24.6% | （旧版本，无此段） |
| 模型自己的思考过程 | 15.6% | 2.5% |
| 写文件 / 改文件的全文（write、edit 参数） | 12.6% | 10.8% |
| 读过的文件全文（read 结果） | 0% | **31.5%** |
| 每次唤醒附带的同一段行为规则 | 5.5% | — |
| 群消息正文 | 5.6% | 5.0% |

两个关键发现：

1. **同样的内容重复了很多遍。** 测试管理者的群消息里，37% 的文字是一模一样的重复：每次被叫醒都附一段 610 字的同样规则（重复 18 次）、「怎么立项」规则（8 次）、同一个项目的完成标准（4–5 次）。而且这些规则和项目方案**系统规则里本来就有**（`rooms/index.ts` 的 `roomRules` 已含 `planText`、`PROJECT_NEXT_STEP`、`INTENT_PLAN_RULE`），唤醒消息里（`turn-prompt.ts` 的 `REASON_LINE`、`collab.ts` 的 `checkContext`）又各附一份，副本永久留在历史里。
2. **项目一变，缓存整段失效。** 系统规则里含进行中项目的方案，项目开始、结束、改方案时规则变了，会话重建，缓存从头失效。数据吻合：测试管理者两次缓存几乎没命中（只命中 2944），都在新项目刚确认后，那两次分别按全价读了约 4 万和 10 万 token。

另外：上游 Pi 对 OpenAI 兼容渠道会把历史里**每一轮**的思考原样回传；渠道会不会对这部分计费、会不会直接忽略，还没实测，记为待确认。

## 3. 方案（用户已批准，按顺序做，每步实测）

目的：回复更快、旧项目不干扰新项目，顺带少花冤枉钱；助理该知道的一样不少。

### 第 1 步：唤醒消息去掉重复（零风险）

系统规则里已经有的内容不再在每条唤醒消息里抄一遍：
- 管理者被叫醒时怎么做（核验、推进、关键点、交付）、怎么立项，只在管理者的系统规则里写一次（`roomRules`）；唤醒消息（`REASON_LINE`）只写这次为什么叫醒。
- 项目方案只在系统规则里（`planText`）；`checkContext` 只附进度清单、卡住提示、唤醒原因和看板。
系统规则每轮按最新状态生成，助理看到的内容不变，也不会读到旧方案。不做「把方案挪出系统规则」：第 3 步之后新项目都从短日记开始，换项目时缓存失效代价很小，不值得引入同步风险。

### 第 2 步：项目交付时把用户原话存进记忆（只增不减）

群聊每轮写入的记忆按安全分层都是草稿（其他助理的话不能直接当成用户事实），平时不作为长期事实想起。交付时（`room_project_done` 成功后）把**用户本人**在这个项目期间的原话 + 交付摘要（做成了什么、文件、还没做的），用可信来源写给管理者一次（复用 `memory.retainTurn`）。其他助理的话照旧只记草稿。

### 第 3 步：交付后整理群会话

项目交付、同群没有别的进行中 / 待确认项目、群空闲时，用 Pi 自带的整理上下文（复用 `runtime.compact(instructions)`）把管理者和参与成员的群会话各整理一次，要求保留：做过哪些项目、做成了什么、文件在哪、关键决定、用户的偏好、答应过用户但还没做的事。原始记录留在会话文件里。交付提示里要求管理者把没兑现的承诺写进交付卡「还没做的」或记成任务。

上线前在开发实测环境用测试助理连续做几个项目，专门测「把上次那份改一下」「还按上次的口味」「接着上次没做完的」「交付前口头答应的小事」。

## 4. 实现中发现的问题和补的保险

- **Pi 整理只总结较早的部分**：最近约 2 万「估算 token」保留原文（`keepRecentTokens`）。Pi 按「字符数 ÷ 4」估算，中文实际 token 数约是估算的两倍，所以保留的原文实际约 5 万 token，整理后会话约 7 万。会话本来就不大时，整理几乎没效果（实测 7.4 万 → 7.3 万）。所以只在读入超过 **15 万** 时才整理（`TIDY_MIN_TOKENS`，可用 `PIA_TIDY_MIN_TOKENS` 调低做实测）。
- **小结状态过时**：附加要求是作为「Additional focus」交给整理模型的，模型常常不理会，小结里会把已交付的项目写成「待确认」。所以加了三道保险：
  1. `tidyInstructions` 把每个项目的真实状态逐条写进去，要求「以这里为准」，并附上用户在群里说过的原话（最多 3000 字），避免偏好和忌口丢失。
  2. 群规则（`roomRules`）里写「已交付的项目（以这里为准；旧总结如果写着还在进行，那是过时的）」，最近 8 个。
  3. 交付提示要求把答应过用户、还没兑现的事写进交付卡的「还没做的」。
- 整理期间群里下一轮要等整理完再开始（`tidyingOf`），免得边整理边说话。
- 第 2 步的「用户原话写进记忆」只对 Hindsight 记忆生效；基础记忆（basic）没有 `retainTurn`，这时靠第 3 步的整理要求和保留的原文。

## 5. 实测（开发实测环境，真实模型，测试助理 + 测试群）

- 第一次整理：17.5 万 → 约 7 万。之后问「还有什么没做完」，回答正确，没被过时小结误导，还记得「甜点以后再说」；「按上次口味推荐早餐」避开了香菜和羊肉。
- 加了三道保险后的第三次整理（8.1 万 → 小结 6051 字）：小结里有「不吃香菜、不吃羊肉」「甜点清单以后再说」，所有项目都写成已交付，「进行中：无」。
- 整理后问「上次说以后再做的那件事，现在做吧」（没提甜点）：管理者认出是甜点清单，三道甜点都避开了忌口。问「上次那份冰箱速查表在哪，把第二天晚餐换成清蒸鱼」：找到了文件，还发现第二天本来就是清蒸鲈鱼，回头确认要换成什么。
- 顺带看到但没处理：不走项目流程时，帮手交付时说一段，管理者又复述一遍。

### 暂不做

- 旧思考是否回传：先实测渠道是否计费再定。
- 单聊不自动整理（单聊每轮已写入记忆，手动整理照旧）。
