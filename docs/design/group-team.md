# 群聊 = 一个 AI 团队（完整设计）

## 一句话

用户自己组建一个 AI 团队（成员叫什么、负责什么都由用户定，管理者也是团队的一员、有自己的角色）。用户说一个想法，团队像一家靠谱的小公司那样：先把事情想清楚、拿出方案给用户确认，然后分工合作、互相配合、层层把关，一直做到交付；用户只是来聊天时，就正常聊天。

## 设计原则

1. **团队本身就会干活，不需要开关。** 该不该推进，由「有没有一件用户确认过的事」决定，不由用户去拨模式。
2. **用户只在真正需要他的时候被打扰**：确认方案、方案要大改、只有他能给的东西（批准、登录、资源）、超出目标的取舍、办法用尽、交付。其余是通知，不是提问。
3. **分工合作**：每件活交给职责最对口的人（管理者自己的职责它自己做）；同事之间直接配合，不是什么都绕到管理者那里。
4. **层层把关**：每个任务有完成标准，交付前有人验收；不合格退回重做。
5. **说人话**：写给用户看的话像人在说话；成员之间的交接准确、具体。
6. **通用**：不预设行业；规则和界面里不出现具体职业的说法。
7. **成本可控，但不拿质量换钱**：不设预算上限（用户定），靠「不空转、不重复」控制花费；不为省钱提前整理上下文、不截断成员看到的内容。

## 1. 团队的两种状态（取代「自主推进」开关）

| 状态 | 什么时候 | 团队在做什么 |
|---|---|---|
| **平时** | 没有在做的项目 | 像普通群聊：用户说话，管理者回应，或点名最合适的成员回答。成员只在被点名时说话。 |
| **项目进行中** | 用户确认了一份方案（可以有好几个） | 按各自的方案分工推进，直到交付或用户叫停。成员之间可以直接沟通。 |

- 状态由系统根据事实切换：方案被确认 → 项目开始；交付完成或用户叫停 → 回到平时。用户不需要也看不到任何「模式开关」。
- 一个群可以**同时做几个项目**（用户定）：每个项目有自己的方案、分工和进度。用户说话时，管理者判断这句话属于哪个项目（调整那个项目），还是一件新事（新立项）；拿不准就用一句话问用户。成员同时参与几个项目时，按项目分别排队干活，不混在一起。

## 2. 用户说话时，管理者先判断来意

| 用户在干嘛 | 团队怎么回应 |
|---|---|
| 聊天、问问题、一两步的小事 | 管理者直接回答，或点名对口成员回答。不立项。 |
| 想做成一件事 | 进入「立项」（第 3 节）。 |
| 项目进行中：补充、改要求 | 小调整直接纳入；影响目标、范围或交付物的大改动，改方案后请用户重新确认。 |
| 项目进行中：问进度 | 管理者用两三句话说清做到哪了、接下来做什么、需不需要用户做什么。 |
| 说「停」 | 停下整个项目（或指定成员），保留进度，说清停在哪。之后说「接着做」就从停下的任务继续（借鉴 CAMEL 的从任务恢复），不用重新立项。 |

## 3. 立项：从一句话到一份方案

1. **想清楚**：管理者先分析要做成什么、怎样算完成、哪些地方不确定。
2. **专业补全**：普通用户往往只有一句话。能按常理定的细节，管理者用专业判断补上，写明「我们这样理解 / 按这些假设」。专业用户说得很清楚，就直接整理。
3. **请教对口成员**：需要专业意见时，管理者先请相关成员出主意（成员在群里简短回答，不开工）。
4. **只问必须问的**：只把真正没法替用户决定、又会影响结果的事（预算、给谁用、个人偏好这类）问用户，一次一两个、给建议选项；答完还不清楚就继续问，直到能定方案。
5. **方案卡**：用大白话写清——
   - 要做成什么；做到什么程度算完成；
   - 我们的理解 / 假设；
   - 分工：每个成员（含管理者）负责什么；
   - 分几个阶段，每个阶段交出什么；
   - **哪几个关键点会请你看一眼**（由管理者判断，例如「出了两个方向请你挑」「初稿出来请你看方向对不对」），其余只通知进度；
   - 最后交给你什么；
   - 需要你提供什么（没有就不写）；
   - 规模感（大概多久、工作量多大，不承诺精确数字；不谈钱）。
6. **用户决定**：「就这么干」→ 项目开始；直接说哪里要改 → 管理者改了再给他看；「先不做」→ 回到平时。用户在群里说「可以」和点按钮效果一样。

## 4. 推进：团队怎么干活

- **拆成任务**：方案里的每个阶段拆成任务；每个任务有负责人（按角色）、要求、完成标准，以及**依赖**（必须等哪些任务完成才能开始）。
- **依赖自动推进**：一个任务验收通过后，所有依赖它的任务**自动开始**，并且系统把前一个任务的成果交给接手的人。交接不靠管理者记得。
- **交接单**：每个任务交付时，除了成果文件，还写一段交接说明——做了什么、东西在哪、接手的人要注意什么、还有什么没做。下一个人拿到的是成果加交接单，而不是整段聊天记录（借鉴 MetaGPT 用文档交接、OpenAI Agents 交接时只带摘要；也更省 token）。
- **项目进度清单**：每个项目有一张随时更新的清单（阶段 → 任务：已完成 / 在做 / 下一步 / 卡住），管理者每次推进都对着它更新。用户点开项目就能一眼看到做到哪了（借鉴 Manus 的 todo 清单）。
- **能并行就并行**：互不依赖的任务同时做。
- **在自己的工位干活**：成员在自己的工作会话里干（不刷屏），阶段性进展和成果发到群里。
- **管理者既是执行者也是协调者**：属于它自己角色的任务它自己做；同时盯整体进度、协调、验收、对用户沟通。
- **不空等**：任务没人在做、管理者手上也没活而项目没完成时，系统叫管理者看一下下一步；连续没有任何进展才提醒用户（只提醒一次）。

## 5. 成员之间直接协作（新增的核心）

真实团队里同事会直接沟通，不是什么都绕到领导那里：

- **找同事**：成员干到一半，可以直接找某个同事——问问题、要材料、提反馈。这句话发在群里（用户也看得到）；对方被叫醒回答（如果对方正在干活，话直接递到他手上，不打断）；回答送回提问的人正在干的活里，他接着往下做。等太久没人回，就告诉管理者。
- **发现上游有问题**：直接找上游负责人说清哪里不对、为什么。上游修改后作为该任务的新版本重新提交、重新验收；下游拿到新版本继续。
- **影响方案的事才找管理者**：比如要改目标、改范围、要加人、两个成员意见不一致，交给管理者拍板（必要时管理者再问用户）。
- **不越权**：不直接改别人的成果，不替别人做决定。
- **拿不准就停下来对齐**：资料不够、理解不准、结果没把握时，先停下来问清楚（问同事；涉及方案找管理者；只有用户能定的才问用户），不硬猜着往下做（借鉴扣子空间的「对齐」暂停）。
- **一个问题一段小对话，有结束、有上限**（借鉴 ChatDev 的轮数上限 + 结束标记、AutoGen 不让同一人连续发言）：提问的人拿到回答就算这段对话结束，回答送回他手上；同一个问题来回 3 轮还没解决，自动交给管理者，不让两个人一直聊下去。

## 6. 把关

- 每个任务交付后，管理者对照完成标准验收（读真实产物）；不合格退回，写清怎么改。
- **事实要有出处**：调研、数据、引用类的成果要附来源；管理者验收时抽查关键事实，拿不准的标出来，不当成确定的交给用户（避开同类产品被诟病的「一本正经地算错」）。
- **验收三种结果**（借鉴 AgentScope GoalPipeline 的 pass / fail / impossible）：通过；退回重做（写清怎么改）；**这条路走不通**——不再原样退回，直接交给管理者换做法或改方案，避免「退回—重做—再退回」死循环。
- **项目级进度检查**（借鉴 Magentic-One 的 progress ledger）：管理者每次推进都对着进度清单回答固定几个问题——做完了没有、是不是在原地打转、有没有进展、下一步谁做、交代他什么。没进展计数 +1，有进展 −1（偶尔一次没进展不报警），**累计到 3 次先写清为什么卡住，再改计划**，而不是原样重试。
- **改计划有几种办法可选**（借鉴 CAMEL Workforce 的恢复策略）：带着改进意见重做、换更对口的成员、把任务拆小、换一种做法、改方案（影响目标 / 范围 / 交付物时要用户重新确认）。管理者先判断失败原因再选。
- 单个任务卡住仍按三级阶梯处理（管理者自己想办法 → 最后提醒必须换做法 → 办法用尽由管理者向用户说明需要什么帮助）；项目级改计划也解决不了时才走到最后一级。
- 每完成一个阶段，管理者用两三句话告诉用户进度（通知，不提问）。
- **关键节点确认**（用户定：由管理者判断）：方案里写明的关键点到了，管理者把要看的东西（几个方向、初稿等）发给用户，等用户挑选或点头再继续；用户迟迟不回，团队先做不受影响的部分，不空等。

## 7. 交付

- 全部完成标准满足后，管理者把最终成果整合好交给用户：成果文件、做了什么、怎么用、还有什么没做或建议下一步。
- 项目结束，回到平时；项目记录（方案、任务、验收历史）保留可查。

## 8. 刹车与成本

- **去掉**：「自主推进」开关；每轮 token 预算（已去）；项目进行中不再用「每轮发言次数」暂停（那是聊天模式防刷屏的，只留给平时状态）。
- **保留**：卡住检测、空转检测、用户随时说「停」、有后果的操作按权限档位审批。
- **上下文按模型配置来，不砍**：用多少由用户配置的模型窗口决定，Pi 在快到窗口上限（窗口 − 16384）时自动整理；用户想早点整理就在模型设置里把上下文调小。我们不另设阈值、不截断工具输出、不为省钱让成员少看东西。省钱只去掉纯重复和空转：管理者被叫醒时看板和上次完全一样就只说「没有变化」（`rooms/logic.ts` 的 `boardDigestOrUnchanged`）；空转靠第 1 步的兜底唤醒规则。
- **不汇报花费**（2026-10-22 用户定）：方案卡、进度通知、交付卡里都不谈花了多少钱，也不做按项目算花费、花费异常提醒；群顶部原有的花费显示保持不变。
- **失败说清楚**：任务失败或返工时，说清为什么、卡在哪。
- **各干各的、少传废话**：成员在自己的工作会话里干活，交接只传成果和交接单，不把大段过程塞进别人的上下文（借鉴 Claude Code 子代理的上下文隔离）。

## 9. 在群里能看到什么（用户定：全部都看）

- 成员之间的每一句沟通（找同事、回答、反馈、交接说明）都显示在群里，像在看一个真实团队聊天。
- 每个成员正在干的活在群里有一条「正在做…」的状态，干完换成结果；很长的执行步骤（命令输出、读过的文件）折叠起来，点开能看全。不对用户藏任何东西，只是不让长日志刷屏。
- 多个项目同时进行时，群里的消息标明属于哪个项目，可以按项目筛选。

## 10. 界面

- **群顶部状态条**：平时只显示成员；有项目在做时列出每个项目「××（阶段 2/4）」，点开看方案、分工和每个任务的进度，以及「停」。
- **聊天里的卡片**：方案卡（确认 / 先不做）、阶段进度通知、交付卡（成果 + 说明）。
- **任务看板**保留，作为细看每个任务的地方。

## 12. 实施步骤（每步单独可用、单独验证；2026-10-22 用户同意调整顺序）

1. **项目与方案**：来意判断规则、立项流程、方案卡、确认后开始项目（一个群可同时有几个项目）；去掉开关；顶部项目状态；老群的自主推进迁移成项目。
2. **去重复**（已缩小，2026-10-22 用户指出不能为省钱降质量）：只做「看板没变不重复发」；提前整理上下文、截断大段输出、限制帮手列表这些会让成员少看东西的做法都不做。
3. **任务依赖与自动交接**（已实现，未打包：`work-items/deps.ts`、`rooms/progress.ts`、`room_project_replan` / `room_project_resume`）：任务加依赖，验收通过后自动开始后续任务，带交接单；并行；项目进度清单；验收三种结果（「走不通」直接改做法）；项目级进度检查与改计划；停下后接着做。
4. **成员直接协作**（已实现，未打包：`rooms/ask-*.ts`、`rooms/asks.ts`、`work-items/rework.ts`、`work-items/upstream.ts`；工具 ask_colleague / answer_colleague / report_upstream / work_rework）：「找同事」能力、回答回送、一个问题来回 3 轮没解决交给管理者、上游返工与重新验收、拿不准就对齐、互相等待超时交给管理者。
5. **进度通知、关键点确认与交付卡**；失败说清楚；群里消息标明项目、可按项目筛选、长执行过程折叠。
6. **单聊也走方案流程；清理**：旧开关、旧确认卡兼容、文档与决策更新。

**第 1、2 步做完先打包，在真实群里实测**（看管理者的来意判断、方案质量），再决定后面怎么调。每一步都用临时数据 + Mock 跑单测和 e2e。

## 12.1 已知风险和对策（2026-10-22 自查）

| 风险 | 对策 |
|---|---|
| 全靠真实模型照规则做，Mock 测不出来 | 第 1、2 步后就打包实测，不等全部做完 |
| 协作放开后调用次数成倍增加 | 不空转、不重复；同事之间一个问题来回有上限；不砍上下文 |
| 普通用户不细看方案就点确认，补全的假设错了 | 方案卡要短，最关键的两三个假设放最显眼处；第一个关键确认点放早（先出草稿 / 方向） |
| 「全部都看」+ 多项目，群里很乱 | 消息标明属于哪个项目、可按项目筛选；长执行过程默认折叠 |
| 成员互相等待卡死 | 等待超时自动交给管理者 |
| 单聊过度规划，啰嗦 | 单聊门槛更高：只有真正多步骤的大事才出方案 |
| 老群的数据（任务、自主推进状态） | 迁移：开着的自主推进转成一个进行中的项目，任务保留 |

## 13. 单聊也走同一套（用户定）

单聊的助理遇到多步骤的大事，同样：判断来意 → 想清楚、专业补全、只问必须问的 → 出方案（含关键确认点）→ 用户确认 → 自己带帮手推进 → 交付。小事和闲聊照常直接做。和群聊共用同一套「来意判断 / 方案卡 / 项目状态 / 交付卡」，只是执行者从「团队成员」换成「助理和它的帮手」。

|---|---|---|
| 钱花了不知道花在哪，失败也照扣 | Manus（Trustpilot 1.2 分）、Genspark | 只保留群顶部原有的花费显示；团队不汇报花费（用户定） |
| 固定流水线，上游错了一路错到底 | MetaGPT、ChatDev | 关键节点确认、下游直接找上游返工 |
| 只讲自主不设确认，专业 / 事实类任务出错 | 扣子空间评测、通用智能体的幻觉问题 | 方案确认、关键点确认、事实要有出处 |
| 协调者抢成员的活，分工形同虚设 | CrewAI 默认关闭「委派」的取向 | 管理者只做自己角色的活，别人的活交给对口成员 |
| 角色写死不能改 | MGX / Atoms、扣子空间 | 角色全由用户定 |

我们和它们不一样的地方：它们大多是「开发框架」或「一个万能助理」；我们是**用户自己组建、角色自定义、过程完全可见的团队**，跑在用户自己的电脑上。

## 15. 已和用户确认的决定（2026-10-21）

- 团队本身会推进，没有开关；有用户确认过的方案就推进。
- 方案确认后，中途由管理者判断关键点请用户看，其余只通知。
- 成员之间的沟通在群里全部可见；长执行步骤折叠，点开可看。
- 一个群可以同时做几个项目。
- 单聊也走「方案 → 确认 → 自主推进 → 交付」。
- 管理者也有自己的角色和职责；属于自己的活自己做，别人的活交给对口成员。

## 15. 第二轮调研：开源的「多 AI 组队」项目（2026-10-22，读源码 / 官方文档）

看了 CAMEL Workforce（Eigent 的内核）、LobeHub 群聊、Magentic-One、AutoGen 群聊、AgentScope、MetaGPT、ChatDev、CrewAI、agency-swarm。

**印证了我们的方向**：交接只传成果 / 交接单而不是整段历史（CAMEL、CrewAI、AgentScope、MetaGPT 都这样）；管理者自己判断下一步（Magentic-One、LobeHub supervisor）；向用户提问一次问完（LobeHub）。

**补进设计的**（已写进上面各节）：

| 做法 | 来自 | 用在哪 |
|---|---|---|
| 验收三种结果，「走不通」直接改做法 | AgentScope | 第 6 节 |
| 项目级进度检查：固定几个问题 + 有进展就回退的卡住计数，到 3 先写原因再改计划 | Magentic-One | 第 6 节 |
| 改计划的几种办法，先判断原因再选 | CAMEL Workforce | 第 6 节 |
| 同事之间一个问题一段对话，3 轮没解决交给管理者 | ChatDev、AutoGen | 第 5 节 |
| 停下后从停下的任务接着做 | CAMEL Workforce | 第 2 节 |

**看了但不采用**：固定流水线阶段（ChatDev，太死，它自己 v2 也改了）；限定「谁能找谁」的通信白名单（agency-swarm，通用产品里成员由用户自定，默认谁都能找谁）；成员只看跟自己有关的消息（MetaGPT 订阅，会让成员少看东西）。

**要避开的坑**：MetaGPT、CrewAI 没有真正的重新规划，卡住就死循环或悄悄失败——所以我们的「改计划」必须是真逻辑；靠模型严格输出格式做决策的系统容易被格式问题带偏（CAMEL、AutoGen 都出过），我们的判断尽量落在工具参数和系统状态上，解析要容错。
