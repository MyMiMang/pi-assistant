# 群聊协作设计（已实现）

状态：已实现（未打包），见 decisions/0006。单聊入口尚未接：核心（work-items/）与来源无关，单聊接入只需提供 setWorkSourceProvider 与 workItemTools。

> 2026-10-19 更新（决策 0014 第 5 步）：每次执行改成负责人派的「帮手」（subagents kind=work），群里看到帮手概况、结果和交付文件，工具步骤留在帮手详情（别的成员点名查某一个帮手才看得到完整步骤，见 `helper-scope.ts`）。下文「在负责人会话里执行」按此理解。

## 两种模式
- **普通聊天**：现有规则。成员之间不能互相唤醒，只回应用户 / 管理者。
- **自主模式**：用户和管理者确认「目标 + 完成标准」后开启。成员之间可以直接 @ 对方协作、交接。

## 角色
- 每个群一个**管理者**：把需求拆成长期任务（work item），分给合适的成员，全局盯进度。
- 任务归**成员**所有：用成员自己的记忆、权限、电脑；记录来源群，进展/结果发回来源群。
- 管理者只在这些时候被唤醒：任务完成、成员报告卡住、用户发言或 @ 它、定时巡检（约 30 分钟）、系统发现停滞。唤醒时读**任务看板 + 简短进展摘要**，不读全量历史。

## 防护（只检测，不设固定次数上限，不提示费用/token）
- 只聊不干活：连续几轮来回没有新产出/进展。
- 卡住没进展：超时无进展。
- 反复卡在同一点：同一错误重复出现。
- 命中即停下并报告管理者；管理者换方法重试 / 改派 / 拆小；仍解决不了、或需要决定/授权时才问用户，并给出明确选项。
- 2026-10-20 用户改定（[0016](../decisions/0016-group-stuck-manager-handles.md)）：卡住、反复卡在同一处、反复退回都走三级阶梯，**不再自动问用户「换方法 / 改派 / 暂停」**：
  1. 第 1 级：叫醒管理者自己处理（看执行记录和最后的错误，带纠正重做、拆小）；
  2. 第 2 级「最后提醒」（管理者介入后仍没进展 / 同一处第 3 次 / 同一负责人重做满 3 次 / 反复退回）：原样重做停用，必须换做法（改派、拆小、自己接手）；每个任务只给一次（按 `final_warning` 事件算，用户的动作清掉）；改派给不同成员会把重做次数清 0，改要求不清；
  3. 第 3 级「已用尽办法」：任务标受阻（待核验的保持待核验），记 `exhausted` 事件，叫醒管理者在群里向用户说清问题、需要用户帮什么或哪个决定无权拍板；系统同时写一份失败总结（目标、试过什么、卡在哪）并推送，作兜底。是通知不是提问。
  - 原因是批准 / 授权、登录凭据（`userOnlyNeed`）时直接问用户要这个具体的东西，不走阶梯。管理者按群目标自己做大部分决定，只有需要用户才能给的帮助、或超出群目标无权拍板的决定才用 `work_ask_user`。
  - 群对话「只聊不干活」（`rooms/collab.ts`）不在这次范围，仍直接请用户。

## 停止
- 群「停止」只停群里的对话回合；长期任务可单个停，也可一键全停。

## 界面
- 聊天 + 任务看板：负责人、状态（进行中 / 卡住 / 等你决定 / 已完成）、最新进展；需要用户决定的事高亮。

## 架构
- 单聊和群聊共用**一套** work-items / runtime 核心。
- 群只通过两个窄钩子接入：①把群里的派活交给任务（dispatch）；②任务进展发回来源群（post progress）。
- 群的每轮上限只管对话回合；任务派出后不占轮次上限，由任务自己的预算（时间/tokens）约束，预算用完或需要用户决定才暂停。
