# 让更多编程命令行工具「按自己原本的方式」在 Pi 里干活（原生 ACP 接法）

接 [cli-models.md](cli-models.md)、[acp-cli-models.md](acp-cli-models.md)，决定见 [0030](../decisions/0030-native-acp-agents.md)。

## 1. 为什么换接法
- 用户要求：把 orca 支持的、能接的编程命令行工具都接进来；没装的在 App 里一键安装，装好点「登录」就能用。
- 已有的「只借脑子」接法（关掉工具自带的读写 / 命令、换掉它的系统提示，动手全交给 Pi）每接一个都要单独摸索，有的关不掉（Grok），工具升级容易失效，也用不上工具自己调好的能力。16 个都这么做不划算。
- orca 的做法：工具按原本的方式干活，orca 只做界面、转达批准请求。我们照这个思路，但保留 Pi 的长处（记忆、群聊、助理电脑、权限档位、中途换模型）。
- 已经接好的 Claude Code / Codex / OpenCode / Antigravity 先保持「只借脑子」，新接法跑稳后再评估要不要迁。

## 2. 用户看到的
- 模型服务页每个工具一张卡片（复用 `CliAgentCard`）：未安装 →「安装」；已安装未登录 →「登录」；已登录 → 能在模型列表里选。卡片显示版本，有新版时提示「有更新」，用户点了才更新（不自动更新）。
- 选了某个工具当模型，用起来就是在 Pi 里用这个工具：对话框、过程、批准卡片都在 Pi 里。
- 工具做的每一步（读写文件、跑命令）在聊天里显示成过程步骤；要批准的照常弹卡片。

## 3. 怎么接（一个通用后端 + 每个工具一份很薄的配置）
- **复用现有 ACP 后端**（`cli-agents/acp-process.ts`、`pi-adapter/cli-models/acp.ts`），加一种「原生」模式：不关工具自带的能力，不替换它的系统提示。
- **Pi 的工具照样给**：经现有工具桥（MCP）把这个助理在 Pi 里本来就有的工具交给它（助理电脑、浏览器、记忆、群聊、发文件等），走 Pi 的审批。
- **告诉它身在何处**：每个会话开头交代「你在 Pi 助理里为用户工作，名字 / 人设是……，除了你自己的工具还能用这些 Pi 工具，什么时候用哪个」。工具支持追加指令就追加，不支持就放在首条消息里。
- **工作地点**：助理自己的工作文件夹（`workspace/<助理 id>`），产出的文件 Pi 里直接能看、能发。
- **权限**：工具自己的 `session/request_permission` 不再一律放行，改成交给 `requests.ts` 按这个助理的权限档位处理（完全权限 → 直接允许；其他档位 → 弹批准卡片）；凭据类路径照常拒绝；暂停「操作电脑」时一律拒绝。
- **工具自带的步骤**：ACP 的 `tool_call` / `tool_call_update` 通知只用来在聊天里显示过程，不交给 Pi 执行（避免执行两遍）；具体怎么显示由第一批实现时提方案、我审过再定。
- **上下文**：中途换模型 / 换工具沿用现有做法（程序把历史排成文字交给新工具，不用模型）；同一工具续用现有会话。
- **整理上下文 / 停止 / 插话 / 用量**：沿用现有 ACP 后端的做法。

## 4. 和用户自己的安装完全分开
- **自己装一份**：不管用户电脑上有没有装，Pi 都装一份自己用，装在 `<数据目录>/cli-agents/<工具 id>/<版本>`，不改全局环境，不用用户的那份。
- **单独的配置目录**：每个工具的家目录 / 配置目录指向 `<数据目录>/cli-agents/<工具 id>/home`（用各工具自己的环境变量，例如 Claude 的 `CLAUDE_CONFIG_DIR`），登录、设置、规则文件、MCP、历史都和用户自己的分开。
- **环境白名单**：复用 `buildCliEnv`，不带用户终端里的模型密钥等变量。
- **每个工具验收时逐条检查**：① 读不到用户全局的规则 / 设置 / MCP；② 不会从工作文件夹往上读到用户目录里的 `AGENTS.md` / `CLAUDE.md`（能关就关）；③ 登录是否真的分开（Mac 钥匙串可能共用，实测后标出）；④ 系统级强制设置（公司下发）挡不住，不处理。挡不住的写进卡片说明。

## 5. 安装、登录、更新
- **安装信息来自 ACP 官方注册表**（agentclientprotocol/registry 的 `agent.json`：npm 包或各平台安装包 + 启动参数 + 部分 sha256）。我们把用到的版本固定写进 `third-party.json`（版本 + SHA256 / npm 完整性），不在运行时临时去注册表找安装地址。
  - npm 包：照 `mcp-install.ts` 的做法 `npm install --prefix` 到我们的目录（npm 从哪来，第一批先确认 App 自带的 Node 里有没有 npm，没有就停下来问）。
  - 安装包：照 `cloudflared-bin.ts` 的做法下载、校验 SHA256、解压。
  - 进度走统一下载管理（`downloads.ts`），下载自动重试已有。
- **登录**：注册表要求每个工具支持两种登录之一，通用处理：
  - Agent Auth：调 ACP `authenticate`，工具自己打开浏览器走官方登录。
  - Terminal Auth：打开一个终端窗口，用它给的参数和环境（加上我们的单独配置目录）运行，用户在里面登录。
  - 我们不碰账号密码和登录凭证。
- **更新**：卡片显示当前版本；检查更新 = 查注册表里的新版本号；用户点「更新」才装新版到新的版本目录，装好后切换；记下测过的版本，没测过的版本提示一句，不阻止使用。

## 6. 分批
1. **第一批**：通用「原生」模式 + 单独安装 / 配置目录 + 登录 + 权限对接，先接 Gemini CLI（npm）、Cursor（安装包）、CodeBuddy 三个，跑通全流程。自动化测试只用假命令（`fake-claude` 那类假 ACP 程序）和 Mock 模型；真实工具只在 `dev:live` 用新建测试助理、用户自己登录后实测。
2. **第二批**：剩下 13 个（Copilot、Amp、Devin、Goose、Auggie、Autohand、Cline、Droid、Kilo、Kimi、Kiro、Mistral Vibe、Qwen Code），每个只加一份配置 + 验收检查；没法真实验证的标「实验性」。
3. 之后再评估：已接的 4 个要不要迁到原生模式；Grok 能否用原生模式接回来。

## 7. 不做
- 不改、不 fork 这些工具，不改 Pi；不自动更新；不读、不存、不转发登录凭证。
- 不用用户电脑上已装的那份，不改用户的全局配置。
- 自动化测试不调用真实工具、不花钱、不碰用户电脑上的任何东西。

## 8. 待验证 / 风险
- 各工具在原生模式下是否每次改文件、跑命令都发批准请求（读文件通常不问 → 凭据拒绝规则对它自己的读文件不一定有效，验收时实测并标出）。
- 工具在用户电脑上（工作文件夹内）直接动手，不在助理电脑里；助理电脑经 Pi 工具可用。
- 各工具单独配置目录用的环境变量要逐个查实；做不到分开的标出。
- 注册表里的版本和安装地址会变，固定版本后随 App 发布更新。
- 人设只能追加，工具自带的系统提示还在：名字、说话方式会生效，但工具本身「写代码、动文件」的习惯更强；验收时实测人设效果并写清楚。
