# 0019 群聊按「AI 团队」重新设计：先出方案、确认后按分工推进到交付
- 日期：2026-10-22
- 状态：有效（取代 0017 里「自主推进开关」、0018「目标清楚由管理者自己开启推进、不等确认」）；其中「不为省钱提前整理上下文」一条已被 [0022](0022-tidy-after-delivery.md) 修订
- 决定：按 [design/group-team.md](../design/group-team.md) 实施。要点：
  - 没有「自主推进」开关；群里有用户确认过的方案（项目）就推进，可同时有几个项目。
  - 管理者先判断来意：闲聊 / 小事直接答；要做成一件事就立项——想清楚、用专业判断补全并写明假设、必要时请教对口成员、只问必须由用户定的一两件事，然后发方案卡；用户确认（按钮或说「可以」）才开工。
  - 方案卡写明目标、完成标准、假设、分工（含管理者自己）、阶段、关键确认点、交付物、需要用户提供什么、规模感；卡片要短，关键假设放最显眼处，第一个关键确认点放早。
  - 推进时按成员角色分工，管理者也做自己角色的活；任务带依赖自动接力并附交接单；成员之间直接配合（找同事、上游返工重新验收、拿不准就对齐）；中途只在管理者判断的关键点请用户看；做完交付。（2026-10-22 用户定：团队不用汇报花了多少钱）
  - 群里成员之间的沟通全部可见，长执行过程折叠；单聊遇到多步骤大事也走方案流程（门槛更高）。
  - 实施顺序：项目与方案 → 去重复（2026-10-22 缩小：不为省钱提前整理上下文或截断内容）→ 任务接力 → 成员直接协作 → 进度 / 关键点 / 交付卡 → 单聊与清理；第 1、2 步后先打包实测。
- 原因：用户 2026-10-21 指出群聊整体设计有问题（零敲碎打的补丁、开关甩给用户、成员不能直接配合、管理者被说成不干活），要一份完整方案；调研了 15 个同类产品后定稿，用户确认。
- 不做什么：不做面向某一行业的定制（如视频生成、配音），生成类能力由用户自己配置；不设预算上限。
- 影响：packages/server/src/rooms/、work-items/、agent-runtime/（规则）、apps/web 群聊界面；后续每步各自更新设计状态。
