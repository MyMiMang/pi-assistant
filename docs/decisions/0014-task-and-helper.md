# 0014 「任务」与「帮手」：任务类机制合并
- 日期：2026-10-19
- 状态：有效
- 决定：
  - 界面上只用两个词：**任务**（有负责人、完成标准、核验，要负责到底的事）和 **帮手**（一次后台执行；界面上取代「子代理」这个词，后台任务、定时任务和主动巡检的每次运行都显示为帮手）。例行（定时）任务和主动巡检只是「什么时候自动开一个帮手」的触发设置。
  - 帮手可以再派帮手，但**最多一层**（主会话 → 帮手 → 帮手，第二层不能再派）。
  - 执行中写的记忆先是草稿；所属任务**通过核验后自动转正**，没通过核验（或不属于任务）就保持草稿，等主会话确认。
  - 按 [design/task-architecture-analysis.md](../design/task-architecture-analysis.md) §5.5 的步骤分步迁移，每步单独可发布；第一步是给后台任务的重启加安全判定（安全就续跑，不安全标「中断待核验」等人继续），复用子代理的判定逻辑。
  - **卡住由负责的会话自己解决，不问用户「继续等 / 停止」**（2026-10-19 用户反馈后修订第 3 步）：
    - 先诊断：工具还在预计时长内、命令还在输出、模型还在流式输出、工作区文件还在变，都算「慢但在动」，不打断；
    - 真卡住时主会话按阶梯处理、目标不变：看记录和最后的错误 → 带针对性纠正从最近检查点重启（结果未知的操作先核验）→ 换做法（改说明派新帮手、拆小或自己接手）→ 办法用尽就结束这个帮手，主会话向用户报告失败总结（目标、试过什么、卡在哪）；
    - 同一原因反复失败要换策略：第 2 次提示，第 3 次起拒绝原样续跑；
    - 只有进展需要用户才能给的东西（批准 / 权限、登录 / 凭据、真正的取舍、只有用户有的资源）才找用户，而且说清楚要什么；
    - 后台 / 定时 / 巡检的帮手没有主会话回合负责，系统自己走机械部分：重启一次，仍卡住就失败并写明试过什么（巡检静默记录）。
  - **群里的帮手**（第 5 步，2026-10-19 用户定）：
    - 群任务的每次执行是负责人派的帮手（kind=work），挂在负责人自己的任务会话上；重启续跑、卡住处理、停止、并发上限都走帮手那一套。执行帮手没有主会话回合负责，卡住时系统重启一次，仍卡住就失败，由群管理者按原流程处理；
    - 群里每个助理都能派自己的帮手，帮手最多再派一层（第二层不能再派；上一层等下一层结束、收齐结果再整合；上一层结束时还在跑的下一层一并停掉）；
    - **角色范围**：有群角色的助理（比如被分配成「编剧」）派帮手时，帮手的系统规则里自动带上：它代表哪个助理 / 角色、这个角色的职责、子任务和完成标准、不归它管的事（其他成员的角色）。帮手不替别的角色干活，也不直接找群成员或协调者（帮手本来就没有群发言工具），超出范围的写明交回派它的助理，由那个助理决定或上报协调者。下一层帮手继承同样的范围；
    - **执行详情可见性**（一个设置 `groupHelperDetail`，默认 owner）：群里人人都能看到每个帮手是谁派的、在做什么、做到哪一步、结果；完整执行详情（工具步骤、命令输出）只有派它的助理和用户能看。改成 group 时群成员都能看完整详情。群任务执行帮手交付的文件是任务结果，直接进群；
    - 执行帮手（含它派的下一层）写下的记忆草稿，在任务这一修订通过核验后自动转正（转到这个助理自己的库）；退回的修订、不属于任务的草稿不动。
  - **派帮手的成本规则**：一两步的小事自己直接做；只有多步骤、耗时长或可并行的工作才派帮手——帮手让主上下文保持精简，但每次都有固定开销（任务说明、它自己的提示词和工具、回报）。帮手回报简短的结果摘要，不回传完整过程。
- 原因：后台任务 / 子代理 / 群任务执行三套容器重复实现了会话、重启、卡住检测、回报和界面，安全性不一致（后台任务重启不判定直接续跑）。用户批准了合并方案。
- 不做什么：不在单聊另建一套群任务执行；帮手不能无限嵌套派生；未核验的执行记忆不自动转正；卡住时不把「要不要等 / 停」丢给用户。
- 影响：agent-runtime/background-tasks.ts、subagents.ts、helper-scope.ts、subagent-driver.ts、subagent-resume.ts、work-items/*、routines.ts、proactive.ts、requests.ts、Tasks.tsx / Subagents.tsx / WorkItems.tsx；设计 design/task-architecture-analysis.md。
