## 判断

Rovai 是有实际 agent 接入与执行管理的同类产品：Host/Core 协调本机 Codex、Claude Code、Pi 等运行时。它值得学习的重点，是把成员身份、当前配置、每次执行的事实和后续待办分清，让用户看懂多成员工作。

**不能因找不到叫 `assign` 的工具就断言它没有派活、只是共享频道。** 主会话抽核发现它有独立的 Task 创建/改派/状态工具，用户与 Default Lead 负责定义责任，Task 本身不唤醒执行，另用带 `taskId` 的消息投递；投递会校验任务仍有效且收件人就是负责人。这是“责任记录与开始执行分开”的设计。它与 Pi Assistant 当前“管理者 `room_assign`、成员顺序发言、回合硬上限”的编排不同，单靠静态审查不能判定谁整体更强、谁更省 token。

## 值得借鉴的六点

| 设计 | 源码可核事实 | Pi Assistant 现状与建议 | 代价与边界 |
|---|---|---|---|
| 当前配置与实际执行记录分开 | 成员设置说明“用于之后开始的新执行”；消息和 Run 的模型信息分别来自自己的 `runtimeModel`。历史缺记录显示“模型未记录”，不拿成员当前设置回填 | 本次修复补齐成员当前模型/强度入口；历史已有模型/用量信息，完整运行级强度展示仍需单独设计。适合后续明确“以后用什么”和“刚才用了什么” | 当前设置提示成本低；真实执行快照需要贯通事件、持久化、旧数据兼容，不能当纯前端小改。记录的是请求配置还是服务实际接受也须分清 |
| 能力读取失败保留选择 | 模型真实选项驱动思考档位；不在当前目录的值标成不适用/未核对；读取失败有保留说明与重试；旧异步结果不能擦掉新能力 | Pi 已有真实档位、加载/失败/重试与代次保护；本次群配置继续复用，并显示换模型后的合法降级。无需为一个 Pi runtime 复制异构 adapter 全套状态机 | 小到中。不要在目录暂缺时把用户配置写成最低档或“不支持” |
| 成员信息就近可见 | 成员列表显示角色、模型/强度摘要、在队/暂离、运行异常，按钮可键盘展开详情 | Pi 现有头像/名字/管理者标记，本次点成员默认概览即可调模型/强度。可后续评估在成员详情增加更清楚的摘要，避免把顶部成员条塞满 | 小到中。长服务名/长模型名、手机触摸、读屏与错误状态要一起考虑 |
| 发送前解释投递方式 | 基于当前收件人和执行能力预览发送/插话/排队；不支持时给具体原因 | Pi 已有插话、引用路由、停止和群内调度。可学习“这条送给谁、何时处理”的短说明；须基于我们实际路由，不能照搬另一个运行时的模式开关 | 中。不能把忙碌统一写成“回合后排队”：Pi 单聊通过 `steer` 在工具边界送达，群聊还需按成员/调度状态准确区分 |
| 独立任务与执行分离 | Task 有负责人、状态、阻塞原因与完成摘要；建立/改派不会自动启动工作，发送时再关联任务 | Pi 已有子代理/后台任务/持久等待和群派活。长期多人目标可先补清“责任、执行结束、整个目标完成”的差异；不急着另建看板与一套平行任务系统 | 中到高。跨重启、重复投递、停止、核验结果和费用都需完整契约；Run 完成不能自动等于任务完成 |
| 成员离队有收尾状态 | UI 展示“正在收拢已开始工作 X/Y”，含停止新消息/工具写入的说明 | Pi 已有移出成员与取消排队。后续应审查仍在执行的工作如何结束，再决定是否展示收尾进度 | 中到高。UI 文案不能证明底层已停；只有服务端掌握可信分母和终态才显示进度 |

## 已有能力、不要误报缺口

- **默认接收人说明已经存在**：`apps/web/src/components/RoomChat.tsx` 输入框工具栏已有“不 @ 人时由管理者回答”和 Help。小容器会隐藏常驻短句，但 Help 仍在。早期审查只搜 `Chat.tsx` 得出的“完全没有提示”结论不成立。后续可评估手机的可发现性，不能为了参考项目再加重复入口。
- **引用和收件人路由已经存在**：Pi 有明确用户引用、群作者目标与成员资格判断。自动挂一条“回复某消息”应来自真实关联记录；成员可能读过多条未读消息，不应猜单一对象。Rovai 本身也有 Run 回复锚点，不能把它的引用设计简单说成不真实。
- **思考档位与跟随/生效分层已经存在**：子代理与本次群成员配置均复用共享组件/模型元数据。服务不同、目录加载失败与模型真的不可调是不同状态。
- **等待不应持续调用模型是共同原则**：Pi 已有事件/持久等待与断点续跑，不需要为参考项目重写等待服务。

## 不建议直接照搬

- 多 adapter 接入、目录世代和各家原生设置带来的整套复杂度。Pi Assistant 继续通过官方 Pi SDK 自有适配层维护，当前没有切换底座的理由。
- 每成员、每会话再叠 Fast 覆盖矩阵。我们应保持已有助理/子代理的清楚作用域，不因参考项目新增配置层。
- 把模型/强度/权限/状态全部挤到顶部成员条。可以借用信息就近展开的方式，字号、换行、触摸命中区和主题仍按自己的组件规范做。
- 在没有执行快照时用当前配置补历史，在没有可信停止状态时写“全部收拢”，或用未知总量画进度。

## 本轮取舍与后续顺序

本次发布只完成用户已经提出的群成员模型/强度配置与技能提议用途说明，不扩大为任务看板、异构运行时或新一层模型配置。

后续先做与可靠性直接相关的事实呈现：① 运行中更改配置的生效范围与保存失败反馈；② 消息/执行真实模型和思考请求快照、缺失不猜；③ 投递与停止状态。独立任务看板/成员收尾进度要先审已有服务端状态与可复用模块，再给小范围设计。

以上是产品/源码评估。跨设备群聊、真实执行质量、停止是否完全阻止后续副作用及各 adapter 兼容性，本次均未实机验证。
